# Calibra Ticket Omnichannel — Provider Requirements

Last verified: **2026-08-15**

## Research policy

Only official/primary provider documentation is accepted as a production contract. A provider is never reported as connected because a switch is enabled or because local configuration exists. `connected` requires live provider evidence and, when the provider uses webhooks, verified webhook evidence. If an official production contract could not be verified, Calibra intentionally exposes the provider as unavailable instead of using scraping, reverse engineering, private APIs, or fake health.

## Important provider restrictions

- WhatsApp templates, conversation windows, business verification, phone-number ownership and current Meta policy are provider-controlled; Calibra must surface provider errors rather than bypass them.
- Telegram Bot API is a bot integration, not a Telegram user-account client. Calibra must never use MTProto user-account automation to imitate a bot integration.
- Instagram messaging availability and scopes depend on the professional-account/login model currently accepted by Meta.
- Rubika/Bale integrations must remain on their documented Bot APIs. Private web-client protocols are out of scope.
- Eitaa remains intentionally unavailable until a current official production contract is verifiable.
- Gmail push depends on an authenticated Google Cloud Pub/Sub push subscription and mailbox watch renewal.
- Microsoft Graph subscriptions expire and require renewal; lack of renewal must degrade health rather than remain green.
- SMS is an adapter family, not one provider. Each concrete provider requires its own source-backed credential form, adapter tests and delivery semantics.

## Connection truth table

| Evidence | State |
|---|---|
| Feature disabled | `disabled` |
| Valid configuration stored, not provider-verified | `configured` |
| Connection/webhook setup currently executing or waiting for webhook verification | `connecting` |
| Provider identity verification succeeded **and** required webhook verification is healthy | `connected` |
| Provider reachable but a required sub-component is unhealthy | `degraded` |
| Provider request/configuration failure | `error` |
| Provider rejected/expired credentials | `expired` |

`enabled != connected` and `configured != connected` are invariant rules.
